## 1. 왜 다시 설계하나

### 1.1. 기존 계획에서 무엇이 "논문 비교"였나

README 3.3절의 필수 비교군 중 **TF-IDF, BGE+kNN, ModernBERT는 논문 라우터가 아니라 "표현 방식" 기준선**이다. 같은 난이도 3단계 목표를 서로 다른 입력 표현으로 푸는 실험이다. 논문 라우터로 필수 지정된 것은 **RouterDC 하나**였고, GraphRouter·CARROT·RouteLLM은 선택 확장이었다.

### 1.2. 최근 문헌에서 확인한 두 가지 사실

1. **라우팅 정체(plateau).** 2026년 연구는 21개 라우터를 5개 벤치마크에서 비교했다. 상위 5개의 정확도 차이는 평균 0.22%p에 불과했고, 모두 oracle보다 10.6~29.4%p 낮았다. **단순한 kNN이 다섯 벤치마크 모두에서 상위 2위 안**이었다([Routing Plateau](https://arxiv.org/abs/2606.07587)). 2025년 연구도 잘 조정한 kNN이 복잡한 학습형 라우터와 비슷하거나 더 낫다고 보고했다([Li 2025](https://arxiv.org/abs/2505.12601)).
   - 쉬운 뜻: "복잡한 라우터가 당연히 이긴다"는 전제를 둘 수 없다. **강한 단순 기준선(kNN)을 반드시 넣어야** 우리 결과를 믿을 수 있다.
2. **라우팅 쏠림(collapse).** 예산 여유가 커지면 라우터가 싼 모델로도 충분한 질문까지 가장 비싼 모델로 보내는 현상이 보고됐다. RouterBench에서는 oracle이 GPT-4를 20% 미만만 쓰는데 라우터는 100% 가까이 썼다([When Routing Collapses](https://arxiv.org/abs/2602.03478)).
   - 쉬운 뜻: 우리 R1→R0 전이 실험에서도 피드백 학습 후 easy 예측이 61%→14%로 줄어드는 **상향 쏠림**이 관찰됐다. 비교 실험에서도 쏠림을 따로 재야 한다.

### 1.3. 우리 라우터의 학술적 위치

대부분의 논문 라우터는 "후보마다 맞힐 확률(또는 점수)을 예측해 가장 좋은 후보를 고른다". 우리 운영 라우터 R0는 **질문의 난이도를 easy/medium/hard로 분류해 단계에 연결**하는, 문헌에서 드문 방식이다. 그래서 **질문 난이도를 명시적으로 모델링하는 IRT-Router**가 학술적으로 가장 가까운 비교 대상이다.

## 2. 비교의 기준이 되는 우리 라우터

| 이름 | 무엇을 예측하나 | 최종 선택 | 현재 상태 |
|---|---|---|---|
| R0 (운영) | 질문 난이도 easy/medium/hard (3-class CE) | 가장 확률 높은 난이도 → low/medium/high 후보 | 운영 1.0, 봉인 test 예측 있음 |
| R1 (연구 승자) | 후보별 성공 확률 (BCE) | 성공 확률 − λ×비용 이 가장 큰 후보 | 봉인 test 예측 있음 |
| R2 | 후보 간 상대 우열 (pairwise) | 점수 − λ×비용 | 봉인 test 예측 있음 |

세 모델은 같은 ModernBERT-base, 같은 train 21,406문항으로 이미 학습돼 있다([1.1절](README.md#observed-objective-results)). 이번 실험에서 **다시 학습하지 않는다.**

**R0의 "비용 손잡이" 문제.** R0는 비용을 고려하는 조절값(λ)이 없어서 비용–품질 곡선이 점 하나로 나온다. 그래서 기존 D_dev nAUC가 0.166으로 낮게 기록됐다. 이는 성능이 나빠서라기보다 곡선을 그릴 수 없어서다. 공정한 비교를 위해 **재학습 없이 R0에 문턱값 τ를 다는 변형(R0-τ)**을 제안한다.
- 규칙: "이 질문이 t단계 이하로 충분할 확률 P(난이도 ≤ t)가 τ 이상인 가장 낮은 단계 t를 고른다."
- τ를 높이면 더 비싼 단계로 보내고, 낮추면 싼 단계로 보낸다. 원래 R0(가장 확률 높은 난이도)는 곡선 위의 한 점으로 함께 보고한다.
- 이 변형은 **우리가 추가한 것**임을 명시한다(9절 결정 항목 2).

### 3.2. 각 라우터를 비교할 만한 이유 (쉬운 설명)

**① kNN 효용 라우터 — "비슷한 문제를 누가 잘 풀었나"를 그대로 따라 한다.**
새 질문과 가장 비슷한 과거 문제 k개를 찾고, 그 문제들에서 각 후보 모델이 맞힌 비율과 쓴 비용의 평균을 낸다. 그 평균으로 "성공률 − λ×비용"이 가장 큰 후보를 고른다. 학습이 없어서 가장 단순하다.
- 비교 이유: 위 1.2절처럼 **최근 연구에서 거의 항상 상위권**인 기준선이다. 우리 라우터가 이것보다 못하면 복잡한 학습이 의미가 없고, 비슷하면 "정체 구간 안"이라는 정직한 결론이 된다.
- 우리 쪽 장점 확인: 우리 서비스는 캐시 조회용으로 **BGE 임베딩을 이미 계산한다.** 그 임베딩을 재사용하면 라우팅 비용이 거의 추가되지 않는다. "이미 있는 임베딩만으로 라우팅하면 어떤가"라는 실무 질문에도 답한다.
- 기존 BGE+kNN(README 3.4절)은 이웃의 **난이도 라벨로 투표**하는 방식이다. 이번 kNN은 이웃의 **후보별 성공·비용을 평균**하는 논문 방식이라 서로 다르다. 둘 다 보고한다.

**② RouteLLM-MF — 추천 시스템처럼 "질문과 모델의 궁합"을 학습한다.**
영화 추천이 "사용자 취향 벡터 × 영화 특징 벡터"로 점수를 내듯, 질문 벡터와 모델 벡터의 조합으로 "이 모델이 이 질문을 잘 풀 점수"를 낸다.
- 비교 이유: 라우팅 논문에서 **가장 널리 쓰이는 비교 기준**이다. IRT-Router와 CARROT도 기준선으로 썼다.
- 차용 방식: 원 논문은 강한/약한 두 모델만 비교한다. 점수 함수 자체는 모델마다 따로 계산되므로 **세 후보에 그대로 적용**하고 "점수 − λ×비용"으로 고른다. 두 모델을 전제한 선호(승패) 데이터 대신, 우리가 가진 후보별 성공 기록으로 학습한다. 이 차이를 결과에 명시한다.

**③ IRT-Router — 시험 문항 분석 이론으로 "문제 난이도"와 "모델 실력"을 나눠서 본다.**
문항반응이론(IRT)은 수능 문항 분석처럼 "이 문제는 얼마나 어렵고, 실력 차이를 얼마나 잘 가르는가(변별도)"와 "이 학생의 실력"으로 정답 확률을 설명한다. IRT-Router는 질문 임베딩으로 문제의 난이도·변별도를 계산하고, 모델마다 실력 값을 학습해 성공 확률을 예측한다.
- 비교 이유: **"질문 난이도"를 명시적으로 추정하는 라우터라 우리 R0와 발상이 가장 가깝다.** R0는 난이도를 3단계로 나누고, IRT-Router는 난이도를 연속된 숫자로 본다. 두 방식 중 무엇이 라우팅에 유리한지, 그리고 **IRT가 추정한 난이도와 우리 난이도 라벨이 얼마나 일치하는지**(해석 가능성)를 함께 볼 수 있다.
- 참고: Routing Plateau 연구에서는 IRT 계열이 하위권이었다. 우리 데이터에서도 그런지 확인하는 의미가 있다.
- 사용 방식: 논문의 MIRT 변형을 후보 3개로 그대로 쓴다. 비용은 논문처럼 "α×성공확률 − β×비용"으로 결합한다.

**④ CARROT — "맞힐 확률"과 "비용"을 따로 예측해 조합한다.**
후보마다 정확도와 비용을 각각 예측한 뒤, 둘의 가중합이 가장 좋은 후보를 고른다. 이 단순한 방식이 이론적으로 최적 속도를 낸다는 증명(minimax)이 있다.
- 비교 이유: **우리 R1과 구조가 거의 같다**(후보별 성공 예측 + 비용 결합). 차이는 비용을 고정 가격이 아니라 **질문마다 예측**한다는 점이다. "비용까지 질문별로 예측하면 나아지는가"를 확인할 수 있다. 추가 외부 평가 후보인 SPROUT 데이터를 만든 논문이기도 하다.
- 차용 방식: 원 코드의 OpenAI 임베딩 호출을 쓰지 않고 로컬 BGE 임베딩으로 바꾼다(README 3.8절 기존 결정과 같다).

**⑤ RouterDC — 질문과 잘 맞는 모델을 "가깝게", 안 맞는 모델을 "멀게" 배운다.**
질문 임베딩과 모델 임베딩 사이 거리를 대조 학습으로 조정해, 잘 푸는 모델이 가까이 오게 만든다.
- 비교 이유: README에서 이미 **첫 공식 비교군으로 정한 방법**이다. NeurIPS 2024 논문이고 공식 코드가 있다. 여러 모델이 동시에 잘 푸는 질문을 잘 다루도록 설계돼, "여러 단계가 다 정답일 수 있는" 우리 상황과 맞는다.

**⑥ EquiRouter — 점수를 맞히는 대신 "순위"를 맞히도록 배운다.**
기존 라우터는 후보별 점수를 예측한 뒤 가장 큰 것을 고른다. 이때 점수 차이가 작으면 작은 오차로 순위가 뒤집혀 비싼 모델로 쏠린다는 것이 이 논문의 진단이다. 그래서 처음부터 후보 간 순위를 학습한다.
- 비교 이유: **1.2절의 쏠림 문제를 직접 겨냥한 가장 최근 방법**이다. 우리 R2(pairwise)도 상대 우열을 배우므로, "순위형 학습끼리" 비교가 된다. 논문이 제안한 쏠림 지표(RCI)를 모든 라우터에 함께 계산한다.
- 주의: 2026년 arXiv 논문으로 아직 학회 검증 전이다. 결과 해석 때 이 점을 밝힌다.

**⑦ Hybrid LLM (선택) — "작은 모델로 충분한가"만 예측한다.**
질문이 작은 모델로 충분할 확률을 예측하고, 문턱값을 넘으면 작은 모델, 아니면 큰 모델로 보낸다. 논문은 이를 "질문 난이도 기반 라우팅"이라고 부른다.
- 비교 이유: **난이도 개념을 쓰는 초기 대표 논문**(ICLR 2024)이다. 다만 두 모델 전용이라, low vs high 두 후보만 쓰는 **별도 부분 실험**에서 R0(두 단계로 축소)와 비교한다. 세 후보 주 결과와 섞지 않는다.

**⑧ GraphRouter (선택) — 질문·과제·모델을 그래프로 연결해 예측한다.**
- 비교 이유: 구조가 전혀 다른 대표 방법이다. 그러나 추론 때 과제(task) 정보가 필요하고, Li 2025에서는 kNN과 비슷한 성능이었다. 예산이 남을 때만 수행한다.

### 3.3. 학습 없는 기준선

README 3.7절의 기준선(항상 싼/중간/비싼 모델, best-single, 사용량 맞춘 무작위, oracle)을 그대로 쓴다. 여기에 하나를 추가한다.

**완벽 검증 cascade.** 모든 질문을 가장 싼 모델부터 보내고, 틀리면 다음 단계로 올린다. "틀렸는지"를 기록된 채점 결과로 바로 안다고 가정한다.
- 비교 이유: 우리 서비스는 사용자가 불만족하면 **상위 모델로 다시 보내는(escalation) 구조**다. AutoMix·FrugalGPT 같은 cascade 논문도 같은 발상이다. 이 기준선은 **cascade 방식이 낼 수 있는 가장 좋은 경우(상한)**다. "처음부터 잘 고르는 라우터"가 "일단 싸게 시작하고 올리는 방식"보다 비용 면에서 얼마나 나은지 보여준다.
- 한계: 실제 cascade는 틀렸는지 판단하는 데 추가 비용과 오류가 있다. 이 상한은 그 비용을 0으로 본 값이다.

## 4. 제외한 라우터와 이유

| 라우터 | 제외 이유 |
|---|---|
| [AutoMix](https://arxiv.org/abs/2310.12963), FrugalGPT | 작은 모델의 답을 LLM이 직접 검증해야 한다. 기록된 결과만으로는 재현할 수 없어, 3.3절의 완벽 검증 cascade로 상한만 비교한다. |
| Router-R1 | LLM 자체가 여러 번 생각하며 라우팅한다. 수십억 파라미터와 추가 LLM 호출이 필요해 우리 CPU 서빙 조건과 맞지 않는다. |
| [MixLLM](https://aclanthology.org/2025.naacl-long.545) | 온라인 학습(contextual bandit)과 지연 시간 제약이 핵심이다. 이는 재학습 효과 실험의 축과 겹치고, 질문 태그 생성에 LLM이 필요하다. |
| [UniRoute](https://arxiv.org/abs/2502.08773) | "처음 보는 새 LLM으로 라우팅"이 핵심 질문이다. 우리 후보 세 개는 고정이다. |
| [EmbedLLM](https://arxiv.org/abs/2410.02223) | 수많은 모델의 표현을 배우는 방법이다. 후보가 3개면 이점이 적어 같은 계열인 RouteLLM-MF로 대표한다. |
| Zooter, Arch-Router | 각각 보상 모델로 답변을 채점하는 과정, 사용자 선호 정책 문서가 필요하다. 목표가 우리와 다르다. |
| 난이도를 LLM이 말로 분석하는 방법(VDAR-Router 등) | 라우팅마다 LLM 호출이 필요하다. 2026년 arXiv 단계라 검증이 부족하다. |

## 5. 공정한 비교 규칙

**데이터.** 기존 통합 A 분할을 그대로 쓴다.
- 학습: D_initial_train 21,406문항 (R0·R1·R2가 학습한 바로 그 데이터)
- 설정 조정·λ 고정: D_dev 3,581문항
- 최종 평가: 봉인 test 7,202문항 (RouterBench 3,473 + xRouteBench 3,729), **설정을 모두 잠근 뒤 한 번만**
- 보조: RouterArena 8,379문항 (난이도 정렬 진단만, 비용·품질 없음)
- 후보: 원천별로 이미 고정한 실제 세 모델(RouterBench: Mistral-7B/Yi-34B/GPT-4, xRouteBench: gpt-oss-20B/gpt-oss-120B/Cogito-671B)과 기록된 성공·비용

**두 가지 인코더 트랙.** 성능 차이가 "방법" 때문인지 "입력 표현" 때문인지 나누기 위해서다.

| 트랙 | 대상 | 규칙 |
|---|---|---|
| 공통 트랙 (주) | kNN, RouteLLM-MF, IRT-Router, CARROT, EquiRouter | 모두 **같은 고정 BGE-large 임베딩**을 입력으로 쓴다. 차이는 방법에서만 나온다. |
| 원형 트랙 | RouterDC, (선택) CARROT-roberta, 원 논문 인코더 재현 | 논문 기본 인코더를 fine-tuning한다. 파라미터 수·학습 시간을 함께 공개하고, "같은 인코더 조건"이라고 부르지 않는다. |

**조정 예산 동일.** 각 방법은 D_dev에서 최대 8개 설정만 시도한다(예: kNN의 k, MF의 차원). 한 방법만 더 오래 조정하지 않는다. test는 조정에 쓰지 않는다.

**비용 조절.** 모든 방법은 λ(또는 R0-τ의 τ)를 바꿔 비용–품질 곡선을 만든다. budget별 λ는 D_dev에서 고정해 test에 그대로 적용한다(README 4.4절).

**반복.** 학습형 방법은 seed 42로 한 번 실행하고, D_dev 상위 2개 방법만 seed 17·73을 추가한다(README 3.9절 계약). kNN처럼 무작위성이 없는 방법은 한 번이다.

**입력 길이.** 주 비교는 512 토큰이다. 8192 운영 조건은 R0만 별도 진단으로 둔다.

## 6. 평가 지표 (쉬운 설명)

| 지표 | 쉬운 설명 | 역할 |
|---|---|---|
| 비용–품질 nAUC | 돈을 조금 쓸 때부터 많이 쓸 때까지, 각 예산에서 얻은 품질을 모두 합친 넓이. 1에 가까울수록 모든 예산에서 좋다. 원천별로 계산해 평균한다. | **주 지표** |
| 같은 비용에서의 품질 | 운영 R0가 쓰는 비용, 그리고 기본 budget .50에 맞췄을 때 각 방법의 평균 품질 | 보조 |
| 같은 품질에서의 비용 | R1의 품질에 도달하는 데 드는 비용 | 보조 |
| 비싼 모델 쏠림 | 가장 비싼 후보 호출 비율과, 더 싸게 같은 품질을 낼 수 있었는데 비싼 걸 고른 비율(RCI) | 쏠림 진단 |
| 라우팅 시간·크기 | CPU에서 질문 하나를 라우팅하는 시간(p50/p95), 모델 파라미터 수, 학습 시간 | 실무 비교 |
| 난이도 해석 | R0의 난이도 확률, IRT-Router의 난이도 값이 벤치마크 난이도 라벨·RouterArena 라벨과 얼마나 일치하는가 | 해석 가능성 |

- 이번에는 **라우팅 시간을 포함한다.** 재학습 실험과 달리 방법마다 모델 크기가 크게 달라서(kNN은 검색만, RouterDC는 인코더 fine-tuning) 시간이 실제로 달라지기 때문이다. 우리 서빙은 CPU VM이므로 CPU batch-1 시간을 잰다. 다만 로컬 측정은 참고값이며 운영 VM 성능이라고 부르지 않는다.
- 차이는 질문 그룹 단위 paired bootstrap으로 신뢰구간을 낸다. 한 원천에서만 이기는 결과는 원천별로 따로 보고한다.

## 7. 가설과 사전 판정

| 가설 | 내용 | 판정 방법 |
|---|---|---|
| H1 정체 | 학습형 라우터들의 nAUC 차이는 대부분 작고, kNN이 상위권이다 | 상위권 방법 간 차이의 신뢰구간이 0을 포함하는지 |
| H2 난이도 방식 | R0-τ는 같은 비용에서 성공 예측형(R1·CARROT·IRT)과 비슷한 품질을 낸다 | 같은 비용 품질 차이가 0.01 이내인지 |
| H3 해석 | IRT-Router의 난이도 값은 우리 난이도 라벨과 양의 상관을 보인다 | 원천별 순위 상관과 신뢰구간 |
| H4 쏠림 | 순위형 학습(EquiRouter, R2)은 점수형보다 쏠림 지표가 낮다 | 같은 budget에서 RCI·비싼 모델 호출 비율 비교 |

- "우리가 최고 성능"을 목표 가설로 두지 않는다. 1.2절 문헌에 비춰 **같은 조건에서 어디쯤인지, 어떤 점이 다른지**를 정직하게 보고하는 것이 목적이다.
- 어떤 결과도 운영 라우터를 자동으로 바꾸지 않는다. 운영 변경은 별도 결정이다.

## 8. 실행 구조와 예산 (구현은 9절 확정 후)

1. **공통 준비 (GPU 약 20분):** 모든 질문의 BGE-large 임베딩을 한 번 계산해 봉인한다(train·dev·test·RouterArena 약 4만 문항).
2. **공통 트랙 학습 (CPU 위주):** kNN·RouteLLM-MF·IRT-Router·CARROT·EquiRouter를 임베딩 위에서 학습하고 D_dev에서 설정을 고른다.
3. **원형 트랙 학습 (GPU 약 1~2시간):** RouterDC를 공식 코드로 후보 3개에 맞춰 재학습한다. 공식 코드가 `test`라는 이름으로 checkpoint를 고르면 우리 D_dev를 연결한다(README 3.8절).
4. **R0-τ, R1, R2:** 기존 checkpoint로 D_dev·test 예측만 다시 만든다(재학습 없음).
5. **잠금:** 모든 방법의 설정·λ를 `selection-lock`으로 고정한다.
6. **최종 평가 (GPU 약 1시간):** 봉인 test와 RouterArena를 한 번 평가하고, CPU 라우팅 시간을 측정한다.
7. **반복:** D_dev 상위 2개 방법에 seed 17·73을 추가한다(GPU 약 1~3시간).

예상 총량은 **T4 약 4~7시간**이다. 첫 단계의 실측 시간으로 다시 추정하되, 방법별 조정 예산은 바꾸지 않는다. 새 LLM 호출이나 유료 API는 쓰지 않는다.

| # | 결정 | 선택지 | 권장 |
|---|---|---|---|

| 3 | 필수 비교 대상 범위 | 6개 전부 / 축소 4개(kNN, MF, IRT, RouterDC) | 6개. 쏠림(EquiRouter)과 비용 예측(CARROT)이 각각 다른 질문에 답한다 |

| 5 | 선택 비교 | Hybrid LLM 2후보 부분 실험, GraphRouter | 예산이 남을 때 Hybrid LLM만 |

확정되면 README 3.3·3.8절의 비교군 표를 이 문서에 맞춰 갱신하고, 그 뒤에 노트북을 만든다.
