# 캐시 실험 (C0/C1/C2/C3) 계획서

작성일: 2026-09-30. 이 문서는 **실행 전 사전 계획**이며 결과 보고서나 운영 변경 승인이 아니다. 전체 사양은 [ML 단일 문서 6장](README.md#cache)을 따르고, 이 문서는 그 사양을 현재 운영 구성과 확보한 데이터에 맞춰 실행 가능한 형태로 고정한다. 실행 코드는 [`ml/notebooks/cache_experiment/`](../../ml/notebooks/cache_experiment/README.md)에 있다(2026-09-30).

**범위 원칙.** 일정에 맞춰 줄이지 않는다. README 6장의 최소 실험(D1, D2, C0/C1/C2)과 선택 확장(C3, 보정 정책, 용량 민감도)을 모두 수행한다. 제외 항목은 10절에 이유와 함께 적는다.

## 1. 목적과 질문

서비스는 LLM을 부르기 전에 캐시를 먼저 본다. 이 실험은 **캐시가 호출과 비용을 얼마나 줄이는지, 그 대가로 틀린 답을 얼마나 재사용하는지, 지연은 얼마나 드는지**를 같은 요청 흐름에서 비교한다.

| 질문 | 비교 | 주 데이터 |
|---|---|---|
| Q1. 완전히 같은 질문의 재사용(exact)만으로 얼마나 절감되는가? | C1 대 C0 | D1 |
| Q2. 의미가 비슷한 질문까지 재사용하면 추가 절감과 추가 오답은 얼마인가? | C2 대 C1 | D1, D2 |
| Q3. 현재 운영처럼 리랭커로 재검증하면 오답은 얼마나 줄고, 재사용과 지연은 얼마나 달라지는가? | C3 대 C2 | D1, D2 |
| Q4. 데이터로 고른 임계값은 운영 설정보다 나은가? | 보정 정책 대 C2·C3 | D2 calibration → D2 test, D1 |
| Q5. 캐시 용량을 제한하면 이득이 얼마나 줄어드는가? | 용량 제한 C1~C3 대 무제한 | D1 (민감도) |

라우터는 운영 1.0(R0 `router-modernbert-r0-a-20260927-v1`)으로 고정한다. 캐시 방식만 바꾸고 라우팅 방법, 재학습, 에스컬레이션은 바꾸지 않는다.

## 2. 비교군

| Arm | 구성 | 설정 |
|---|---|---|
| C0 | 캐시 없음 | 매 요청 라우터 → 선택 단계의 기록 답변. 운영 `CACHE_ENABLED=false`와 같이 임베딩도 하지 않는다 |
| C1 | exact만 | 운영 `QuestionHash`와 같은 정규화 키 |
| C2 | exact → semantic(코사인만) | BGE-large, 후보 5개, 항목별 임계값 0.80 |
| C3 | exact → semantic → 리랭커 재검증 | 코사인 ≥ 0.8774 **그리고** `quora-distilroberta-base` 점수 ≥ 0.03581769. **현재 운영 구성** |
| C_cal | exact → (D2 calibration에서 고른 정책) | 7절 규칙으로 한 번 봉인 |
| C1~C3-capN | 위 구성 + 용량 N(LRU, `updated_at` 기준) | N = 2,000 / 1,000 / 500. 운영에는 용량 제한이 없다 |

주 결과는 **현재 운영 설정값 그대로**의 C0~C3이다. 모든 비교군은 빈 캐시에서 시작하고, 정답 여부를 보고 저장을 거르지 않는다(운영처럼 틀린 답도 저장).

## 3. 운영 재현 충실도

결과를 "지금 배포된 캐시의 성능"으로 말하려면 하네스가 운영 코드와 같은 판정을 내려야 한다. 다음을 코드와 테스트로 고정한다.

| 대상 | 방법 | 확인 |
|---|---|---|
| exact 키 | `QuestionHash.normalize/of`를 파이썬으로 재구현. Java `Character.isWhitespace`는 파이썬 `isspace`와 다르다(NBSP 제외 등) | 운영 Java 코드로 뽑은 해시 18개를 테스트 fixture로 고정 |
| 조회 SQL | `SELECT_SQL`, `SELECT_EXACT_SQL`, `INSERT_SQL`, recordHit를 **실행 시점에 `CacheService.java`에서 읽는다** | 테스트가 SQL 조각을 확인 |
| 항목 임계값 | `cache_entry.threshold`는 REAL이라 0.80이 float32(0.800000012)로 저장되어 double 유사도와 비교된다. 메모리 재생도 같은 값을 쓴다 | 테스트 |
| 리랭커 판정 | `RerankGateService.evaluate` 규칙(AND 조건, 최고 점수 채택, 재정렬, 실패 시 미스) | 테스트 |
| 모델 수치 | 서빙 이미지와 같은 torch 2.5.1 / transformers 4.48.3, 같은 revision, 한 문장씩 CLS·L2 정규화, 리랭커는 요청 단위 배치 + sigmoid | **운영 패리티 관문**(아래) |
| HNSW | 주 재생은 정확 코사인 검색. pgvector HNSW와 다를 수 있으므로 trace 하나를 실제 pgvector + 운영 SQL로 재생해 판정 일치율을 보고 | 05 노트북 |

**운영 패리티 관문.** 2026-08-30 배포 스택이 반환한 73개 프로브의 코사인과 리랭커 점수(`experiments/results/rerank-endtoend/results.json`)를 실행 환경이 허용 오차 10⁻⁴ 안에서 재현해야 준비 단계가 진행된다. 사전 확인 결과는 다음과 같다.

| 장치 | 코사인 최대 차이 | 리랭커 점수 최대 차이 | 최상위 후보·판정 불일치 |
|---|---:|---:|---:|
| CPU (2026-09-30) | 2.6×10⁻⁷ | 4.1×10⁻⁶ | 0 |
| Apple GPU(MPS) (2026-10-02) | 7.9×10⁻⁷ | 2.3×10⁻⁶ | 0 |

서빙은 CPU에서 돌지만, 대량 추론은 Colab GPU에서 한다(9절). 이 관문이 그 차이를 실행할 때마다 확인한다. GPU는 TF32를 끈 fp32로 계산한다. 보고서에는 판정 점수가 임계값 ±10⁻⁴ 안에 있어 장치 차이로 뒤집힐 수 있는 판정의 수를 함께 적는다.

## 4. 데이터

### 4.1 공통 pool

- **원천:** 봉인 continual 분할의 D_stream 5,368문항(RouterBench 4,684 / xRouteBench 684). 운영 R0가 학습·튜닝에 쓰지 않은 질문이다.
- **요청 문자열:** stream의 `query_text`. 라우터가 본 사용자 질문이며 캐시 키와 임베딩 입력이다.
- **기록 답변:**
  - RouterBench: stream의 점수·비용은 **5-shot 실행**에서 왔다(0-shot 원본과는 low 단계 점수 1,490건 불일치, 5-shot과는 0건). 그래서 `routerbench_5shot.pkl`의 응답을 기록 답변으로 쓴다. 5-shot 프롬프트 전체를 키로 쓰면 공통 예시 때문에 유사도가 부풀므로 키는 `query_text`로 둔다. 라우팅 데이터와 같은 결합 방식이다.
  - xRouteBench: `llmrouter_generic` train/test에 단계 모델(gpt-oss-20b / gpt-oss-120b / cogito-v2-1-671b)의 **응답, 정답(ground_truth), 채점 방식, 응답 시간**이 있다. 기존 계획의 미확인 항목을 해소했고 포함한다.
  - 준비 단계가 행마다 기록 점수·비용이 stream과 같은지 확인하고, 다르면 멈춘다.
- **서비스 입력 한도:** BGE 토큰(특수 토큰 포함) 512를 넘는 질문은 pool에서 제외한다(사전 확인 33문항, 0.6%). 512토큰을 넘으면 캐시가 질문 전체를 볼 수 없으므로 **캐시 대상이 될 수 없다**(2026-10-02 결정). 운영도 같은 날 이런 질문을 잘라서 처리하던 방식을 거절(400)로 바꿨다(#50, serving #11). 이를 되돌리는 PR(#52, serving #12)이 열려 있지만, 되돌려지더라도 이 실험의 제외 기준은 유지한다.
- **라우터 판정:** 서비스처럼 **요청 원문**(`query_text`)을 운영 R0 패키지로 분류한다(8192 절단). 모델 파일 4개의 SHA를 고정한다. 로컬은 `r0-release-20260927/approved`를, Colab은 전이 실험 kit이 Drive에 올린 바이트 단위로 같은 사본을 쓴다.
  - 재학습 효과 실험의 로거 로그(`logger-log.parquet`, SHA `bcbaafa0…`)는 학습 입력인 `model_input_text`로 추론한 것이다. 그래서 로그를 그대로 쓰지 않고 **관문**으로 쓴다: 로컬 라우터가 같은 입력 200건에서 로그 판정을 99% 이상 재현해야 한다(사전 확인 100건 100% 일치).
  - 사전 확인에서 원문으로 분류하면 판정의 약 9%가 로그와 달랐다. 학습 입력과 서빙 입력이 다르다는 뜻이며, 두 판정의 불일치표를 진단으로 보고한다. 이 차이를 고치는 것은 이 실험의 범위가 아니다.
- 2026-09-30 사전 확인: 결합 누락 0건, exact 중복 0건, 빈 기록 답변 54건(기록 그대로 사용).

### 4.2 재사용 채점기

다른 질문의 답이 나가면 README 6.2절대로 **현재 질문 기준으로 다시 채점**한다.

| 대상 질문 | 정답 | 판정 |
|---|---|---|
| 같은 질문(같은 그룹) | — | 기록 점수 그대로 |
| RouterBench 객관식(MMLU·ARC·HellaSwag·WinoGrande) | 공개본에 정답이 없어, 1.0점을 받은 모델들의 선택이 **모두 같을 때만** 그 글자를 정답으로 복원 | 선택 글자와 그 선택지 문장이 **둘 다** 현재 질문의 정답과 맞으면 정답, 둘 다 틀리면 오답, 엇갈리면 unknown. 선택지를 고르지 않은 답은 오답 |
| xRouteBench 객관식 | `ground_truth` 글자 | 같은 규칙 |
| xRouteBench GSM8K·MATH·AIME | `ground_truth`의 최종값 | `\boxed{}`·`####`·마지막 수를 비교. 수가 아니면 표기 일치만 정답, 나머지 unknown |
| 그 외(RouterBench GSM8K·MBPP·MT-Bench, xRouteBench SQuAD·코드) | 없음 | unknown |

unknown은 전부 실패로 본 **보수적 품질**과 전부 성공으로 본 **낙관적 품질**의 범위로 보고하고, 분모에서 빼지 않는다. 채점 가능 문항은 객관식 3,931, 수치 152, 정답 복원 불가 객관식 79, 채점 불가 1,206이다.

**채점기 자기 일치 검사.** 각 기록 답변을 "다른 질문의 답"처럼 자기 질문에 채점해 기록된 성공 여부와 비교한다. 사전 확인에서 판정 4,074건 중 4,071건(99.93%)이 일치했고, 9건은 unknown이었다. 불일치 3건은 모두 수치형이며 보고서의 한계로 남긴다.

### 4.3 D1: 반복 요청 재생 (비용·품질 주 실험)

- **pool:** 4.1 pool(512토큰 초과 제외)에서 D2 원질문 300개를 뺀 약 5,035문항.
- **trace:** 요청 **4,000개**. 반복 비율 r로 정확히 round(r × 4,000)개 위치(첫 요청 제외)가 이미 보낸 질문을 다시 보낸다. 다시 보낼 질문은 그때까지 나온 서로 다른 질문 중에서 균등하게 뽑는다. 새 질문은 seed별로 한 번 섞은 순서의 앞부분을 쓰므로, 같은 seed의 r 조건들은 같은 새 질문 순서를 공유한다.
- **조건:** r = 0 / 10 / 30 / 50% × seed 3개(20260930~32). r은 관측된 서비스 비율이 아니라 민감도 조건이다. 같은 (r, seed)의 trace는 모든 비교군이 똑같이 받는다.
- **재생:** 히트면 저장된 답을 비용 0으로 반환하고, 미스면 라우터가 고른 단계의 기록 답변·비용을 쓰고 저장한다. 운영 `ChatService`처럼 semantic 히트로 답한 질문은 새로 저장하지 않으므로, 그 질문이 다시 오면 exact가 아니라 다시 semantic으로 처리된다. exact 히트가 다른 질문의 답을 내면 정규화 버그로 보고 즉시 멈춘다(모든 비교군).
- **용량 민감도(Q5):** C1~C3에 용량 2,000 / 1,000 / 500을 걸어 같은 trace로 재생한다. 가득 차면 `updated_at`이 가장 오래된 행을 지운다. 운영 스키마에 이미 있는 열만 쓴다.

### 4.4 D2: 의미적 재사용 검증 (안전성 주 실험)

- **규모:** README 제안 그대로 **300그룹 / 900문항**(원질문 300 + 변형 600). calibration 100그룹 / test 200그룹.
- **그룹:** 원질문 1 + 같은 뜻의 다른 표현 1 + 뜻이 달라지는 함정 질문 1.
- **원질문 선정:** D_stream 중 기록 답변이 비어 있지 않은 문항을 층별로 순서 독립 해시로 뽑는다.

| 층 | 그룹 | 함정 유형 |
|---|---:|---|
| RouterBench 객관식 | 129 | 부정, 개체, 숫자·단위, 시간, 순서 |
| RouterBench 수학(GSM8K) | 51 | 숫자·단위, 순서, 시간 |
| RouterBench 개방형(MBPP, MT-Bench) | 21 | 코드 언어, 출력 형식, 개체 |
| xRouteBench 객관식 | 51 | 부정, 개체, 숫자·단위, 시간, 순서 |
| xRouteBench 수치(GSM8K, MATH, AIME) | 27 | 숫자·단위, 순서, 출력 형식 |
| xRouteBench 개방형(SQuAD, 코드) | 21 | 코드 언어, 출력 형식, 개체 |

  층마다 1/3을 calibration에 배정한다. README 6.2절의 긴 질문 slice(앞 512토큰이 같고 뒤 조건만 다른 질문)는 두지 않는다. 512토큰을 넘는 질문은 캐시 대상이 아니므로(4.1절) 잘린 임베딩 때문에 생기는 오탐은 이 시스템에서 일어날 수 없다. 처음 배정했던 24그룹은 위 층에 나눴다.
- **작성:** 사람이 직접 쓴다(README 6.2절). 변형은 작성 시트로 받고, 비어 있거나, 공백만 다르거나, 512토큰을 넘으면 거부한다.
- **주석:** 두 사람이 서로 보지 않고 `semantic_equivalent`(Y/N)와 `cached_answer_correct_for_target`(Y/N/U)를 판정한다. 시트에는 작성 의도(표현/함정)를 숨기고 순서를 섞으며, 시트 id도 의미 없는 값으로 바꾼다(run001 시트는 실제 id라 주석 도구가 id를 가린다). 불일치는 조정 시트로 따로 결정하고 사유를 남긴다. 원판정, 일치율, Cohen's κ를 모두 보존한다.
- **캐시 상태:** 그 split의 원질문 + D1 pool 전체(배경)의 기록 답변. 배경이 있어야 다른 질문을 잘못 가져오는 오류가 생길 수 있다. 변형 질문은 서로 독립적으로 조회하고 캐시에 넣지 않는다.
- **품질 표시:** 작성 메모에 `low-quality trap`(선택지 구조상 자연스러운 함정을 만들 수 없어 메타 질문이 된 경우)이나 `source anomaly`(원본 문항 자체의 산술 오류·모호성)가 붙은 그룹은 그대로 평가에 포함한다. 그와 별도로 이 그룹들을 뺀 지표를 test 결과에 민감도 분석으로 함께 낸다. 원질문은 00에서 봉인되므로 해당 그룹을 다른 문항으로 바꾸지 않는다.
- **판정:** 자기 원질문에 히트하면 `semantic_equivalent`가 N일 때 재사용 관계 오류(F), 답 정오는 `cached_answer_correct_for_target`으로 정한다. 다른 질문에 히트하면 항상 F이고, 같은 뜻의 표현이면 원질문 정답으로 4.2 채점기를 적용하며 나머지는 unknown이다. 새 표현에 대한 모델의 생성 결과는 없으므로 미스는 품질에 섞지 않는다.

D3(PAWS·QQP 공개 문장쌍)는 10절에서 제외한다.

## 5. 지연(latency) 측정

**05 노트북만 로컬 Mac에서 실행한다**(9절). GCP 없이 잴 수 있는 구간과 없는 구간을 구분한다.

| 구간 | 측정 방법 | 판정 |
|---|---|---|
| exact 키 조회 | 로컬 pgvector 컨테이너(`--cpus=2`)에서 운영 `SELECT_EXACT_SQL` | 로컬 실측 |
| BGE-large 임베딩 | 서빙과 같은 버전·revision, torch 스레드 2(운영 VM 코어 수), 한 문장씩 | 로컬 실측 |
| 벡터 검색 | 운영 `SELECT_SQL`, HNSW, 캐시 500 / 2,000 / 4,000행 | 로컬 실측 |
| 리랭커 | 후보 5개 배치 | 로컬 실측 |
| 라우터(ModernBERT) | 00과 같은 운영 R0 패키지, 8192 절단, CPU. 표본 100건을 다시 분류해 00의 판정과 같은지 함께 기록 | 로컬 실측 |
| HNSW 근사 오차 | 상위 5개가 정확 검색과 같은 비율, trace 하나의 pgvector 재생 판정 일치율 | 로컬 실측 |
| **LLM 생성 시간** | xRouteBench만 기록된 `response_time`이 있다. RouterBench에는 없다 | xRouteBench만 기록값 사용 |
| 서비스 간 왕복 | Spring(서울)↔FastAPI(미국 서부) | **측정 불가.** 8월 운영 관측 약 120ms를 FastAPI 호출마다 더하는 **가정값** |

- 각 구간은 warm-up을 빼고 500회로 p50·p95·최대 메모리를 기록한다. Mac의 절대값이 운영 VM과 같다고 주장하지 않고 **비교군 사이의 상대 비교**에 쓴다.
- **end-to-end 지연**은 요청마다 실제로 수행한 연산(조회·임베딩·검색·리랭커·라우팅)에 구간 p50을 더한 **시뮬레이션**이다. 생성 시간을 포함한 값은 xRouteBench 요청에서만 낸다.
- 참고로 8월 운영 관측은 miss 약 15초, exact hit 5ms, semantic hit 약 200ms, 리랭커 적용 후 약 1.2초였다([exact-match 보고서](../../experiments/results/exact-match/REPORT.md)). 이번 실험은 이 값을 대체하지 않는다.

## 6. 지표

README 6.5절을 따른다. N=전체 요청, H=캐시 답변 수, F=재사용 관계가 틀린 답변 수, E=실제로 오답인 캐시 답변 수다.

| 지표 | 쉬운 뜻 |
|---|---|
| hit rate (H/N), exact/semantic 분리 | 캐시에서 답한 비율 |
| false reuse among hits (F/H), per request (F/N) | 캐시 답 중 다른 질문의 답을 잘못 준 비율 |
| 답 오류 among hits (E/H, 보수·낙관) | 캐시 답이 실제로 틀린 비율 |
| 호출 절감률, 기록 비용 절감률 | C0 대비 LLM 호출·비용이 줄어든 비율 |
| 품질 변화(보수·낙관) | 같은 trace에서 C0 대비 품질 차이 |
| 연산 수 | 임베딩·검색·리랭커 쌍·라우팅 호출 수. 연산 단가를 채우면 달러로 환산 |
| 재사용 가능 문항 recall (D2) | 저장 답이 맞는 변형 중 자기 원질문에 히트한 비율 |
| 구간별 지연 p50·p95, 메모리 | 5절 |

통계: D1은 질문 그룹 단위 paired bootstrap(2,000회)으로 C0 대비 차이의 95% 구간을 내고 seed별 값을 따로 보고한다. D2는 false reuse의 95% Clopper–Pearson 구간과 층·함정 유형별 결과를 낸다.

## 7. 보정 정책(C_cal)

- calibration 변형 200개마다 코사인 상위 16개 후보와 그 리랭커 점수를 한 번 계산하고, 격자의 모든 정책을 같은 후보표로 평가한다.
- 격자: 코사인 0.70~0.99(0.005 간격) × {코사인만, 리랭커(후보 1/4/8/16 × 점수 13단계)}.
- 목표: **hit 중 false reuse ≤ 1%** 조건에서 재사용 가능한 hit 최대화. 동점이면 리랭커 없는 정책 → 후보 수가 적은 정책 → 엄격한 임계값 순이다.
- 만족하는 정책이 없으면 exact만 쓰는 정책으로 봉인하고 그 사실을 기록한다.
- `frozen-policy.json`으로 한 번만 봉인한다. test는 봉인 후 **한 번만** 평가하며, 실행 직전 `test-lock.json`을 쓰고 두 번째 실행은 거부한다.
- 1%는 제안 목표이지 검증된 운영 보장값이 아니다. calibration에서 경계에 맞춘 값이므로 test에서 넘을 수 있고, 그대로 보고한다.

## 8. 사전 판정 기준

1. **C1(exact):** 오탐이 원리적으로 0이어야 한다. 0이 아니면 정규화 규칙 버그로 보고 실험을 멈춘다.
2. **안전성:** D2 test에서 각 정책의 false reuse among hits와 95% 상한을 보고한다. 상한이 5%를 넘으면 "해당 설정의 semantic 재사용은 안전성 근거 부족"으로 기록한다. test hit가 약 200건이면 오류 0건이어도 상한이 약 1.5%라 **1% 이하 보장은 주장하지 않는다.**
3. **C3 대 C2:** 오탐 감소량, 잃은 정탐(재사용 감소), 추가 지연을 함께 보고한다.
4. **비용:** 반복 비율별 호출·비용 절감률과 손익분기(캐시 연산비 < 회피한 생성비)를 보고한다. 반복이 적어 손해인 조건도 그대로 남긴다.
5. **재현성:** 운영 패리티 관문 실패, 라우터 anchor 관문 실패, 기록 점수·비용 불일치, 같은 (r, seed) trace 불일치 중 하나라도 있으면 결과를 만들지 않는다.

운영 캐시 설정은 이 결과로 자동 변경하지 않는다.
