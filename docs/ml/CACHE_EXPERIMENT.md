# 캐시 실험 (C0/C1/C2/C3) 계획서

작성일: 2026-09-30. 이 문서는 **실행 전 사전 계획**이며 결과 보고서나 운영 변경 승인이 아니다. 전체 사양은 [ML 단일 문서 6장](README.md#cache)을 따르며, 이 문서는 그 사양을 현재 운영 구성과 확보된 데이터에 맞춰 실행 가능한 범위로 고정한다. 실행 코드는 아직 없다.

## 1. 목적과 질문

서비스는 LLM을 부르기 전에 캐시를 먼저 본다. 이 실험은 **캐시가 호출과 비용을 얼마나 줄이는지, 그 대가로 틀린 답을 얼마나 재사용하는지, 지연은 얼마나 드는지**를 같은 요청 흐름에서 비교한다.

| 질문 | 비교 |
|---|---|
| Q1. 완전히 같은 질문의 재사용(exact)만으로 얼마나 절감되는가? | C1 대 C0 |
| Q2. 의미가 비슷한 질문까지 재사용하면(semantic) 추가 절감과 추가 오답은 얼마인가? | C2 대 C1 |
| Q3. 현재 운영처럼 reranker로 재검증하면 오답이 얼마나 줄고 지연·재사용은 얼마나 줄어드는가? | C3 대 C2 |

라우터는 운영 1.0(R0 `router-modernbert-r0-a-20260927-v1`)으로 고정한다. 캐시 방식만 바꾸며 라우팅 방법, 재학습, 에스컬레이션은 바꾸지 않는다.

## 2. 비교군

| Arm | 구성 | 설정 |
|---|---|---|
| C0 | 캐시 없음 | 매 요청 라우터 → 선택 모델 기록 답변 |
| C1 | exact만 | 운영 `CacheService`와 같은 정규화 키 |
| C2 | exact → semantic(코사인만) | BGE-large, 후보 5개, 코사인 0.80 |
| C3 | exact → semantic → reranker 재검증 | 코사인 ≥ 0.8774 **그리고** `quora-distilroberta-base` 점수 ≥ 0.03581769 — **현재 운영 구성** |

주 실험은 **현재 운영 설정값을 그대로** 쓴다. 이 실험의 1차 질문이 "지금 배포된 캐시가 어떤가"이기 때문이다. 임계값을 바꿔 가며 본 곡선은 D2 calibration 분할에서만 그리며, test 결과를 보고 임계값을 다시 고르지 않는다. 모든 arm은 빈 캐시에서 시작하고, 정답 여부를 보고 저장을 결정하지 않는다(운영처럼 틀린 답도 저장).

## 3. 데이터

### 3.1 D1: 반복 요청 재생 (비용·품질 주 실험)

- **원천:** 봉인 continual 분할의 D_stream 중 RouterBench 문항. R0가 학습·튜닝에 쓰지 않은 질문이다.
- **답변:** RouterBench 원본(`ml/data/raw/routerbench_*shot.pkl`)에는 11개 모델의 **답변 텍스트·채점 점수·비용**이 있다. 선택된 단계 모델(Mistral-7B / Yi-34B / GPT-4)의 기록 답변을 반환·저장한다. 준비 단계에서 `sample_id`로 원본과 결합하고, 결합되지 않는 행은 사유와 함께 제외한다.
- **xRouteBench:** 원본에 답변 텍스트가 있는지 아직 확인하지 않았다. 준비 단계에서 확인해 있으면 포함하고, 없으면 제외한 이유를 manifest에 남긴다.
- **라우터 예측:** 재학습 효과 실험 00이 만드는 anchor의 8192 로거 로그(`retraining-effect/logger/logger-log.parquet`)를 재사용한다. 같은 모델·같은 질문이므로 다시 추론하지 않는다.
- **trace:** 요청 2,000개. 각 요청은 확률 r로 이미 나온 질문을 다시 보내고(반복), 아니면 새 질문을 뽑는다. **r = 0 / 10 / 30 / 50% × trace seed 3개**. r는 관측된 서비스 비율이 아니라 민감도 조건이다. 같은 r·seed에서는 네 arm이 완전히 같은 trace를 받는다.
- **채점 한계:** RouterBench 공개본에는 문항별 정답(gold)이 없고 모델별 채점 결과만 있다. 그래서 다음과 같이 채점한다.
  - exact hit와 같은 duplicate group 안의 hit: 저장한 답변의 기록 점수를 그대로 쓴다.
  - **다른 질문의 답이 재사용된 semantic hit:** "재사용 관계 오류(F)"로 센다. 정답 여부는 unknown으로 두고, 전부 실패로 본 보수적 품질과 전부 성공으로 본 낙관적 품질의 범위를 함께 보고한다.
  - 원 벤치마크에서 gold를 찾아 다시 채점하는 작업은 이번 범위 밖이다.

### 3.2 D2: 의미적 재사용 검증 (안전성 주 실험)

- **구성:** 그룹 하나 = 원질문 1 + 같은 뜻의 다른 표현 1 + 뜻이 다른 함정 질문(hard negative) 1.
- **원질문:** D1과 겹치지 않는 D_stream RouterBench 문항 중, 선택 모델의 기록 답변이 있는 것에서 뽑는다.
- **함정 유형:** 숫자·단위, 부정, 개체, 시간, 순서, 코드 언어, 출력 형식 변경. 앞부분은 같고 뒤 조건만 다른 긴 질문도 포함한다.
- **주석:** 두 사람이 독립적으로 `semantic_equivalent`(같은 뜻인가)와 `cached_answer_correct_for_target`(저장된 답이 이 질문에도 맞는가)을 판정한다. 불일치는 조정하고, 원판정과 근거를 모두 보존한다.
- **규모 기본값:** calibration 50그룹 + test 100그룹 = **150그룹·450문항**(README 제안 300그룹의 절반). test hit가 약 100건이면 오류 0이어도 95% 상한이 약 3%이므로, **"오탐 1% 이하"를 입증할 수 있는 규모는 아니다.** 결과에도 이 한계를 표시한다.
- **평가 방법:** 원질문의 기록 답변을 캐시에 넣고, 다른 표현과 함정 질문으로 조회해 hit·오탐·재사용 정답성을 잰다. 새 표현에 대한 모델의 생성 결과는 없으므로 miss는 unknown으로 두고 품질에 섞지 않는다.

D3(PAWS·QQP 공개 문장쌍)는 보조 진단이라 이번 범위에서 제외한다.

## 4. 지연(latency) 측정

**GCP 없이 로컬에서 잴 수 있는 것과 없는 것을 구분한다.**

| 구간 | 측정 방법 | 판정 |
|---|---|---|
| exact 키 조회 | 로컬 PostgreSQL 컨테이너에서 운영과 같은 조회 | 로컬 실측 |
| BGE-large 임베딩 | 운영 serving 이미지와 같은 모델·revision, Docker `--cpus=2`, torch 스레드 2 | 로컬 실측 (운영 VM e2-standard-2와 같은 코어 수) |
| 벡터 검색 | 로컬 pgvector 컨테이너, 운영과 같은 HNSW 인덱스·후보 5개, 캐시 크기별 | 로컬 실측 |
| reranker | 운영과 같은 모델·revision, 후보 5개 배치, 같은 CPU 조건 | 로컬 실측 |
| 라우터(ModernBERT) | 같은 CPU 조건, 질문 길이별 | 로컬 실측 |
| **LLM 생성 시간** | 공개 데이터에 기록이 없음 | **측정 불가** |
| 서비스 간 네트워크 왕복 | Spring(서울)↔FastAPI(미국 서부) 왕복 | **측정 불가**. 8월 운영 실측 약 120ms를 참고값으로만 표기 |

- 각 구간은 warm-up 요청을 제외하고 요청 500개 이상으로 p50·p95·최대 메모리를 기록한다. Mac의 절대값이 운영 VM과 같다고 주장하지 않고, **arm 사이의 상대 비교**에 쓴다.
- **end-to-end 지연**은 로컬 실측 구간 + 가정한 LLM 시간(예: 8월 운영 실측 miss 약 15초)을 더한 **시뮬레이션**으로 따로 표시한다. 캐시의 지연 이득은 대부분 "LLM 호출 회피"에서 오므로, 회피한 호출 수(정확히 측정됨)와 함께 보고한다.
- 참고로 8월 운영 실측은 miss 약 15초, exact hit 5ms, semantic hit 약 200ms, reranker 적용 후 약 1.2초였다([exact-match 보고서](../../experiments/results/exact-match/REPORT.md)). 이번 실험은 이 값을 대체하지 않는다.

GCP를 쓰더라도 LLM 생성 시간은 얻을 수 없다. 실제 Claude를 불러야 하므로, 필요하면 소규모 실측(티어별 수십 회)을 별도 선택 항목으로 둔다. 기본 범위에는 넣지 않는다.

## 5. 지표

README 6.5절을 따른다. N=전체 요청, H=캐시 답변 수, F=재사용 관계가 틀린 답변 수, E=실제로 오답인 캐시 답변 수다.

| 지표 | 쉬운 뜻 |
|---|---|
| hit rate (H/N) | 캐시에서 답한 비율 |
| false reuse among hits (F/H) | 캐시 답 중 다른 질문의 답을 잘못 준 비율 |
| 호출 절감률 | C0 대비 LLM 호출이 줄어든 비율 |
| 순비용 절감률 | 기록 비용 기준으로 C0 대비 줄어든 비율 |
| 답변 품질 변화 | 같은 trace에서 C0 대비 품질 차이(unknown 범위 포함) |
| 구간별 지연 p50·p95, 메모리, 인덱스 크기 | 4절 |

통계는 원질문 group 단위 paired bootstrap으로 arm 차이의 95% CI를 내고 trace seed별 변동을 따로 보고한다.

## 6. 사전 판정 기준

1. **C1(exact):** 오탐이 원리적으로 0이어야 한다. 0이 아니면 정규화 규칙 버그로 보고 실험을 멈춘다.
2. **C2·C3(semantic):** D2 test에서 false reuse among hits와 95% CI 상한을 보고한다. 상한이 5%를 넘으면 "현재 설정의 semantic 재사용은 안전성 근거 부족"으로 기록한다. 3절의 규모 한계 때문에 1% 이하 보장은 주장하지 않는다.
3. **C3 대 C2:** 오탐 감소량, 잃은 정탐(재사용 감소), 추가 지연을 함께 보고한다.
4. **비용:** 반복 비율별 순비용 절감률과 손익분기(캐시 연산비 < 회피한 생성비)를 보고한다. 반복이 적어 손해인 조건도 그대로 남긴다.

운영 캐시 설정은 이 결과로 자동 변경하지 않는다.

## 7. 실행 환경과 예산

- **전부 로컬(Mac)에서 실행**한다. 임베딩 약 5,000문항은 MPS로 수 분이며, 시뮬레이션은 CPU로 충분하다. 라우터 예측은 재학습 실험의 로거 로그를 재사용하므로 GPU가 필요 없다.
- 지연 측정만 Docker(`--cpus=2`)와 로컬 PostgreSQL+pgvector 컨테이너를 쓴다.
- GCP·Colab·유료 API 호출 없음. 사람 주석(D2)이 가장 큰 비용이다.

## 8. 범위에서 제외

- D3 공개 문장쌍 진단, 캐시 용량·TTL 민감도, warm start
- 다른 라우터와의 결합, 재학습·에스컬레이션과 캐시 갱신의 결합
- 원 벤치마크 gold를 이용한 cross-question 재채점
- LLM 생성 시간과 서비스 간 네트워크 지연의 실측(4절)
- 운영 캐시·DB 변경

## 9. 실행 순서

1. **데이터 준비:** D_stream RouterBench와 원본 답변 결합, xRouteBench 답변 확인, pool manifest
2. **D2 작성·주석:** 가장 오래 걸리므로 먼저 시작한다
3. **하네스 구현:** trace 생성기, 운영과 같은 exact 정규화·semantic 검색·reranker 판정, 채점과 unknown 범위, 테스트
4. **D1·D2 실행**과 **지연 측정**
5. 보고서를 `experiments/results/cache-experiment-v1-<실행일>/`에 반입하고 README 6장에 요약
