## 1. 결론

대화형 질문에서 운영 C3는 **함정을 12.7%만 통과시켰다**(D2 72%). 대신 **같은 뜻 질문도 50.5%만 재사용했다**(D2 89%).
D2에서는 "위험하게 많이 재사용"했고, 대화형 질문에서는 "안전하지만 절반을 놓치는" 쪽으로 기울었다.

같은 뜻과 함정을 구분하는 능력 자체는 두 데이터에서 비슷하게 낮다(AUC 코사인 0.725, 리랭커 0.726 / D2 0.683, 0.686).
단독 구분력은 리랭커와 코사인이 같지만, 틀리는 문항이 서로 달라 함께 쓰면 이득이 있다. 함정 통과율을 12.7%로 맞추면
같은 뜻 재사용은 코사인만 33.7%, 리랭커만 43.5%, 운영 AND 규칙 50.5%다(5절). 원인은 5절에 정리했다.

우리 서비스 사용자가 가장 많이 물을 **프로그래밍 분야에서는 함정 통과(31%)가 같은 뜻 재사용(20%)보다 많았다.**

## 4. 해석과 한계

- **D2의 72%가 운영 오탐률이 아니었던 것처럼, 이번 12.7%도 운영 오탐률이 아니다.** 실제 트래픽의 함정 비중을 모른다.
  다만 "대화형 질문이면 함정을 덜 통과시킨다"는 방향은 이번 데이터로 확인됐다.
- **그 대가로 재사용이 절반으로 줄었다.** 92문항에서 잰 recall 90.5%도 일반화되지 않았다. 58쌍으로 정한 기준은
  D2에서는 너무 느슨했고, 대화형 질문에서는 너무 엄격했다. 기준을 고른 데이터 밖에서 어느 쪽으로든 맞지 않는다.
- 리랭커 단독 구분력(AUC)은 코사인과 같지만, 함께 쓰면 같은 함정 통과율에서 같은 뜻을 더 많이 살린다(5.4절).
  초안에서 "리랭커는 기준을 하나 더 거는 것뿐"이라고 쓴 해석은 이 비교로 틀린 것이 확인되어 고쳤다.
- 데이터 한계: 문장 작성과 라벨이 모두 Claude다(작성 의도 기준, 사람 판정 없음). 함정 유형이 entity에 치우쳤다(139/300).
  10개 미만 유형(output_format, negation, superlative)은 방향만 본다. 영어만 다뤘다.
- 운영 HNSW 근사 검색 대신 정확한 코사인을 썼다. PR #53의 pgvector 재현에서 top-k recall이 0.99 이상이었으므로 영향은 작다.
- 이 데이터로 임계값을 다시 고르지 않았다.

## 5. 원인 분석 (`diagnose.py`, `results/diagnosis.json`)

같은 데이터 안의 사후 분석이다. 자기 원질문과의 쌍 점수로 계산했다.

### 5.1 단어 겹침이 정답과 반대 방향을 가리킨다

| | 단어 Jaccard 중앙값 |
|---|---:|
| 가벼운 바꿔쓰기 | 0.250 |
| 크게 바꾼 바꿔쓰기 | 0.273 |
| 함정 | **0.714** |

단어 겹침으로 같은 뜻과 함정을 가르면 AUC 0.037이다. 거의 완벽하게 **반대로** 맞힌다. 같은 답이 필요한 질문은 표현이
바뀌어 단어가 적게 겹치고, 다른 답이 필요한 질문은 단어 하나만 바뀌어 거의 다 겹친다. exact 캐시가 완전히 같은 질문을
먼저 처리하므로, 의미 캐시까지 오는 질문은 원래 이런 구조다. 데이터를 일부러 어렵게 만든 결과라기보다 의미 캐시 문제의
본질에 가깝다.

리랭커 점수는 같은 뜻 질문 안에서 단어 겹침과 함께 움직였다(Spearman 0.33). 표현이 많이 바뀐 같은 뜻 질문일수록
점수가 낮다. 리랭커 자체 경계 0.5로 보면 같은 뜻 질문의 41%만 "같은 질문"으로 봤고, 41%는 운영 기준 0.036에도 못 미쳤다.

### 5.2 대상이 바뀐 함정은 잡고, 관계가 바뀐 함정은 놓친다

| 함정 유형 | 리랭커 중앙값 | C3 통과 |
|---|---:|---:|
| output_format | 0.0551 | 33% |
| direction | 0.0256 | 43% |
| scope | 0.0221 | 32% |
| negation | 0.0081 | 14% |
| polarity | 0.0063 | 24% |
| superlative | 0.0055 | 0% |
| time | 0.0028 | 10% |
| number_unit | 0.0010 | 6% |
| entity | 0.0005 | 4% |
| code_language | 0.0003 | 0% |
| (참고) 크게 바꾼 바꿔쓰기 | 0.0545 | — |
| (참고) 가벼운 바꿔쓰기 | 0.1947 | — |

Python→Java, 반지름→지름, 대상 이름처럼 **핵심 단어가 바뀌면** 리랭커가 확실히 다르게 본다. 반대로 핵심 단어는 그대로 두고
변환 방향, 범위, 형식, 긍정/부정이 바뀌면 점수가 크게 바꾼 바꿔쓰기와 같은 수준에 머문다. 리랭커는 무엇에 대한 질문인지는
보지만 그 사이의 관계나 조건은 잘 보지 못한다.

단어 집합이 완전히 같고 순서만 바뀐 함정 5개 중 3개가 통과했다(string↔integer 0.965, timestamp↔date 0.986,
list↔string 0.856). 같은 구조의 km↔miles 0.018, Celsius↔Kelvin 0.013은 막혔다. 같은 구조인데 분야에 따라 점수가
0.01과 0.99로 갈렸다.

### 5.3 문장이 길수록 코사인이 무뎌진다

| 원질문 길이 | 그룹 | 코사인 AUC | 리랭커 AUC |
|---|---:|---:|---:|
| 7단어 이하 | 108 | 0.849 | 0.761 |
| 8단어 이상 | 192 | 0.650 | 0.707 |

긴 문장에서는 단어 하나가 바뀌어도 문장 벡터가 거의 움직이지 않는다. 벤치마크 문항처럼 긴 질문으로 만든 D2에서 코사인
AUC가 0.683으로 낮았던 것과 같은 방향이다.

### 5.4 같은 함정 통과율에서의 비교

| 방식 (함정 통과 12.7%로 맞춤) | 같은 뜻 재사용 |
|---|---:|
| 코사인만 | 33.7% |
| 리랭커만 | 43.5% |
| 코사인 + 리랭커 logit 표준화 합 (AUC 0.765) | 47.2% |
| 운영 AND 규칙 | **50.5%** |

임계값 선택이 주된 원인은 아니다. 운영 AND 규칙은 이 데이터에서 단순 조합 중 가장 나은 지점에 가깝다. 기준을 올리든
내리든 AUC 0.73~0.77의 같은 곡선 위에서 움직일 뿐이다.

### 5.5 프로그래밍 분야는 구분력이 무작위보다 낮다

| 분야 | 코사인 AUC | 리랭커 AUC | 리랭커 중앙값 (크게 바꾼 바꿔쓰기 / 함정) |
|---|---:|---:|---|
| general | 0.943 | 0.910 | 0.352 / 0.0005 |
| everyday | 0.843 | 0.844 | 0.110 / 0.0016 |
| writing | 0.826 | 0.809 | 0.913 / 0.0037 |
| cs | 0.773 | 0.729 | 0.053 / 0.0007 |
| math_science | 0.719 | 0.782 | 0.162 / 0.0013 |
| **programming** | **0.387** | **0.427** | **0.0015 / 0.0052** |

프로그래밍에서는 함정이 같은 뜻 질문보다 원질문에 더 가깝게 나왔다. 두 가지가 겹친다.
- 같은 뜻 질문이 `python biggest number in a list`, `js fetch a url, get example`처럼 짧은 채팅체·약어라,
  Quora의 문장형 질문으로 학습한 리랭커가 다른 질문으로 본다.
- 함정 유형이 scope 15 · polarity 10 · direction 등 관계가 바뀌는 쪽에 몰려 있다. 다른 분야는 리랭커가 잘 잡는
  entity가 절반 이상이다.

### 5.6 정리

1. 의미 캐시까지 오는 질문은 단어 겹침이 정답과 반대 방향을 가리키는 구조다.
2. BGE는 주제가 같은지, quora 리랭커는 핵심 단어가 같은지를 주로 본다. 둘 다 "같은 답이 필요한가"를 직접 판단하지 않는다.
3. 그래서 핵심 단어가 같고 관계·조건만 바뀐 질문(방향, 범위, 형식, 긍정/부정)과, 표현이 크게 바뀐 같은 뜻 질문에서 동시에 틀린다.
4. 문장이 길수록 코사인이, 채팅체·약어일수록 리랭커가 약해진다. 프로그래밍 질문은 둘 다에 해당한다.
5. 임계값 조정으로는 넘을 수 없다. 개선하려면 조건(언어, 방향, 숫자, 형식)을 비교하는 별도 신호나,
   "같은 답인가"를 직접 학습한 판정기가 필요하다.

## 6. 판정기 개선 비교 (PLAN2.md, `tune.py`, `results/tuning.json`)

calibration 108그룹에서 기준을 고르고 test 192그룹(같은 뜻 384, 함정 192)에서 한 번 평가했다. 선택 규칙은 calibration
함정 통과율 5% 이하에서 같은 뜻 재사용 최대. 검색은 운영과 같고 판정만 바꿨다. NLI·LangCache 점수는 Cloud Build에서
계산했다(sentence-transformers 5.7.0).

| 방법 | 기준 | 같은 뜻 재사용 [95%] | 함정 통과 [95%] | hit 중 오재사용 (함정 10%) |
|---|---|---:|---:|---:|
| M0 운영 C3 | 고정 | 49.5% [44, 55] | 12.5% [8, 18] | 2.7% |
| M0+G 운영 C3 + 조건 규칙 | 고정 | 49.2% [44, 54] | 8.3% [5, 13] | 1.8% |
| M1 C3 재튜닝 | 코사인 0.93, quora 0.020 | 24.2% [20, 29] | 4.7% [2, 9] | 2.1% |
| M2 NLI 양방향 함의 | 0.030 | **68.0%** [63, 73] | **4.2%** [2, 8] | 0.7% |
| M3 LangCache 임베딩 | 0.914 | 21.6% [18, 26] | 5.2% [3, 9] | 2.6% |
| M4 조건 규칙 + C3 재튜닝 | 0.93, 0.020 | 24.2% [20, 29] | 3.6% [1, 7] | 1.6% |
| M5 조건 규칙 + NLI | 0.030 | 67.4% [63, 72] | 3.6% [1, 7] | 0.6% |
| M6 조건 규칙 + LangCache | 0.896 | 24.2% [20, 29] | 5.2% [3, 9] | 2.3% |
| M7 로지스틱 결합 | 0.753 | **85.2%** [81, 89] | **4.7%** [2, 9] | 0.6% |

- 모든 방법에서 같은 뜻 질문이 다른 원질문에 재사용된 경우는 0이었다.
- 조건 규칙은 calibration에서 tech, antonym, direction, format만 켜졌다(함정 차단이 같은 뜻 차단의 3배 이상).
  proper_noun(31 대 17), negation(6 대 7), scope(3 대 13), numbers(9 대 5)는 같은 뜻 질문도 많이 막아 꺼졌다.
- M7 표준화 가중치: NLI 함의 +1.42, NLI 모순 −1.66, LangCache −0.39, 조건 규칙 −0.26, quora +0.08, 코사인 +0.04.
  결합 모델은 거의 NLI에 기대고 있다.

### 해석

- 5절에서 진단한 약점(핵심 단어는 그대로 두고 관계·조건이 바뀌는 함정)을 NLI가 거의 그대로 막았다. NLI는 문장 사이의
  논리 관계(함의·모순)를 학습한 모델이라, "같은 질문인가"를 배운 quora 리랭커보다 "같은 답이 필요한가"에 가깝다.
- 캐시 전용으로 미세조정한 LangCache 임베딩은 이 데이터에서 BGE보다 나아지지 않았다. 두 문장을 따로 압축하는
  bi-encoder의 한계가 남는다.

### 한계 (중요)

- **데이터, 조건 규칙, 결합 모델이 모두 같은 분포에서 나왔다.** test는 calibration과 다른 그룹이지만 같은 작성자(Claude)가
  같은 방식으로 만든 질문이다. 결과가 낙관적일 수 있다. 운영 반영 전에 독립 데이터(팀원 D2, 사람이 판정한 실제 서비스
  질문)에서 다시 확인해야 한다.
- 지연을 재지 않았다. NLI(DeBERTa-v3-base, 약 1.8억 파라미터)를 후보마다 양방향으로 돌리면 quora 리랭커보다 느리다.
  운영 VM(CPU 2코어)에서 실측이 필요하고, small·xsmall 모델이나 1위 후보만 검증하는 방식도 비교해야 한다.
- 결합 모델(M7)은 108그룹으로 학습했다. 가중치가 안정적인지 여러 분할로 확인하지 않았다.

## 7. 판정 지연과 모델 크기 (2026-10-11)

### 7.1 측정 방법

- **운영 실측:** 게이트웨이 VM에서 운영 FastAPI를 직접 호출했다(`cloud/live_rerank.py`). 호출 사이 0.3초 휴식.
  연결 왕복(health) p50 242.7ms, 리랭커 짧은 질문·후보 5개 486.4ms, 후보 1개 323.5ms, 긴 질문(약 350자)·후보 5개
  1,444.8ms, 임베딩 855.9ms. 모델 계산분은 왕복을 뺀 값이다(후보 5개 약 244ms).
- **격리 비교:** Cloud Build(Intel Xeon 2.2GHz)에서 torch 스레드를 운영 VM(e2-standard-2, vCPU 2, Broadwell)과 같은 2로
  묶고 모델별로 55회 쟀다(`cloud/bench.py`). 같은 조건의 quora와 운영 실측의 비율(2.07, 2.22, 2.15배, 평균 2.14배)을
  곱해 운영 지연을 추정했다.

### 7.2 결과 (모델 계산분 p50, 운영 추정)

| 판정 모델 | 짧은 질문, 후보 5개 | 짧은 질문, 1위 후보만 | 긴 질문, 1위 후보만 |
|---|---:|---:|---:|
| quora 리랭커 (현재) | 253ms | 78ms | 267ms |

NLI는 함의를 양방향으로 보므로 후보 하나당 두 번 계산한다.

### 7.3 같은 분할에서의 정확도 (test 192그룹, 함정 통과 5% 기준으로 calibration 선택)

| 판정 | 같은 뜻 재사용 | 함정 통과 |
|---|---:|---:|
| 운영 C3 (참고) | 49.5% | 12.5% |
| NLI base | 68.0% | 4.2% |
| NLI base, 1위 후보만 | 68.5% | 4.2% |
| NLI small | 74.2% | 6.8% |
| NLI xsmall | 72.1% | 5.7% |
| NLI xsmall, 1위 후보만 | 71.9% | 5.7% |
| NLI distilroberta-base | 32.3% | 4.2% |

- 1위 후보만 검증해도 정확도가 떨어지지 않았다. 이 데이터에서 같은 뜻 질문이 다른 원질문에 재사용된 경우가 없어서다.
- DeBERTa-v3 계열만 효과가 있었다. distilroberta·MiniLM NLI는 빠르지만 같은 뜻 재사용이 30% 안팎으로 떨어졌다.
- **NLI xsmall로 1위 후보만 검증하면 운영 추정 185ms로 지금 리랭커(후보 5개 약 244ms)보다 빠르다.** 같은 뜻 재사용은
  49.5%에서 71.9%로, 함정 통과는 12.5%에서 5.7%로 좋아졌다.
- 결합 모델(LR)은 quora 점수와 LangCache 임베딩을 추가로 계산해야 해 그만큼 지연이 더 든다.

### 7.4 한계

- 운영 VM에서 NLI를 직접 재지 않았다. quora 기준 배율로 추정했으므로, DeBERTa가 오래된 Broadwell CPU에서 다르게
  느려지면 오차가 생긴다. 반영 전에는 운영과 같은 e2-standard-2에서 직접 재야 한다.
- 메모리는 프로세스 RSS 차이로 쟀는데 모델 파일을 메모리 매핑해 값이 실제보다 작게 나와 보고하지 않는다.
  파라미터 수 기준으로 xsmall 약 7천만, small 약 1.4억, base 약 1.8억이다. 운영 VM 메모리는 8GB다.
- 정확도는 6절과 같은 데이터·같은 작성자의 결과다. 독립 데이터 검증 전에는 운영 반영 근거로 쓰지 않는다.
