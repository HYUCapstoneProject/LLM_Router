# exact match 캐시 계층 실측

측정일: 2026-08-30
대상: **배포된 운영 스택** (Cloud Run → nginx → GCE Spring → PostgreSQL/pgvector)
관련 커밋: `90358d1`, 마이그레이션 `05-exact-match-cache.sql`

## 1. 왜 넣었나

리랭커 도입 검토 중에 드러난 문제다. **완전히 동일한 질문도 매번
FastAPI `/router/embed` 를 왕복했다.**

FastAPI 서빙은 `us-west1`, 게이트웨이는 `asia-northeast3` 에 있어
왕복만 약 120ms 다. 글자까지 같은 질문에는 그 비용을 낼 이유가 없다.

또한 exact match 는 **오탐이 원리적으로 0** 이다. 문자열이 같으므로 임계값을
볼 필요도 없다.

## 2. 결과 — 배포 후 실측

같은 질문을 연속으로 던졌다.

| 회차 | 질문 | 캐시 | 토큰 | 서버 지연 |
|---|---|---|---:|---:|
| 1 | `What is the chemical symbol for gold?` | miss | 14 in / 10 out | **15,063 ms** |
| 2 | 위와 **완전히 동일** | **exact hit** | 0 / 0 | **5 ms** |
| 3 | 앞뒤 공백만 추가 | **exact hit** | 0 / 0 | **3 ms** |

**15,063ms → 5ms.** 3회차가 히트한 것은 정규화가 동작한다는 뜻이다.

비교를 위해 같은 시점의 시맨틱 히트는 약 200ms, 리랭커 게이트를 켠 뒤에는
약 1,178ms 다. exact 히트는 **리랭커를 부르지 않으므로 그 영향도 받지 않는다.**

## 3. 설계에서 정한 것

### 정규화는 Java 한 곳에서만 한다

앞뒤 공백 제거 + 내부 연속 공백 축약. SHA-256 을 떠서 `cache_entry.question_hash`
에 저장한다. **SQL 에서는 정규화하지 않고 저장된 값을 비교만 한다.**

양쪽에서 정규화하면 두 구현이 어긋나는 순간 인덱스 조회가 **예외 없이 조용히**
빗나간다. 캐시가 안 맞는데 아무도 모르는 상태가 된다.

### 대소문자는 정규화하지 않는다

exact match 의 유일한 존재 이유가 "오탐 0" 인데 소문자화는 그 보장을 깬다.
대소문자만 다른 질문은 임베딩 경로로 넘어가 0.99 근처에서 히트한다.

### ⚠️ 여기서 실제 버그가 하나 잡혔다

정규화 정규식을 `"\s+"` 로 썼는데, **Java 15 부터 문자열 안의 `\s` 는 정규식
공백류가 아니라 리터럴 스페이스 이스케이프**다. 컴파일은 통과하면서
탭·줄바꿈만 조용히 안 걸렸다.

정규식을 버리고 `Character.isWhitespace` 로 한 번 훑는 방식으로 바꿨다.
이스케이프 사고가 원천적으로 없고 유니코드 공백까지 잡는다.
`QuestionHashTest` 의 탭·줄바꿈 케이스가 이 버그를 잡았다.

## 4. 집계를 exact / semantic 으로 나눈 이유

`request_log.cache_match_type` 에 `exact` / `semantic` 을 남긴다.

**둘을 합친 히트율을 시맨틱 캐시 성능으로 제시하면 과대평가가 된다.**
"같은 질문을 다시 쳤다"는 임베딩이 한 일이 아니기 때문이다.

분석 API 는 `semanticHitRate` 를 따로 내려주며, **분자·분모 모두에서 exact 를
제외**한다. exact 히트였던 요청은 시맨틱 캐시가 판단할 기회조차 없었으므로
분모에 넣으면 안 된다.

## 5. 특별히 봐야 할 사항

**(1) 05 마이그레이션 이전 캐시 행은 `question_hash` 가 NULL 이다.**
백필하지 않았다. 그 행들은 exact match 를 타지 못하고 시맨틱 경로로만 히트한다.
운영 DB에 그런 행이 남아 있어(2026-08-30 기준 7건 중 5건), **시연 전 초기화하면
자연히 해소된다.** 같은 행이 리랭커 게이트에서도 채점 불가 대상이 된다.

**(2) 15,063ms 는 캐시 미스 전체 시간이다.** embed + classify + Claude 호출이
모두 들어 있고 그중 Claude 가 대부분이다. exact match 가 아낀 것은
embed 왕복(약 120ms)과 벡터 검색이지 15초 전부가 아니다.
**"15초를 5ms로 줄였다"는 표현은 오해를 부른다** — 정확히는
"이 질문에 대해 LLM 호출 자체를 건너뛰었다"이다.

**(3) 표본이 3건이다.** 동작 확인이지 성능 벤치마크가 아니다.

**(4) 첫 요청이 콜드 스타트면 20~30초가 나온다.** 컨테이너 재시작 직후 실측에서
29,393ms 를 관측했다. 시연 전 웜업이 필요하다.

## 6. 재현

배포된 프론트에 같은 질문을 두 번 보낸다.

```bash
curl -sS -X POST "<프론트URL>/api/chat" \
  -H 'Content-Type: application/json' \
  -d '{"message":"What is the chemical symbol for gold?","conversationId":"t"}'
```

`scripts/reset-demo-data.sh --warm <프론트URL>` 이 초기화 후 예열까지 한 번에 한다.
